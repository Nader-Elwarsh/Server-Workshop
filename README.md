# الورشة الفنية — Workshop Mini

نظام إدارة ورشة صيانة أجهزة منزلية يعمل كتطبيق **PWA** قابل للتثبيت. التطبيق **محلي أولًا**: يحتفظ ببيانات التشغيل والإعدادات محليًا في `IndexedDB` (قاعدة `wfOperationalDB`)، والصور/التسجيلات في مخازن IndexedDB؛ وعند توفر Firebase وتسجيل الدخول يزامن البيانات المدعومة مع السحابة ويتيح بوابة العملاء.

عند عدم توفر الشبكة أو Firebase يظل التطبيق قابلًا للاستخدام محليًا، وتبقى التعديلات المعلقة قابلة للرفع عند عودة الاتصال. المزامنة ليست بديلًا عن النسخ الاحتياطي؛ استخدم التصدير الدوري من إعدادات النظام.

## الأقسام

- 👥 العملاء وعناوينهم وملفاتهم
- 🔧 الأجهزة المرتبطة بكل عميل
- 🛠️ أوامر الشغل: الحالات، الحسابات، قطع الغيار، الصور، التحصيل والإغلاق
- 📦 المخزن وقطع الغيار وحركات المخزون
- 💳 الحسابات والمحافظ والتحويلات المرتبطة بأوامر الشغل
- 💰 الخزنة النقدية المستقلة عن حسابات المحافظ
- ✅ المهام والمتابعة
- 🗺️ خط السير اليومي والقادم، مجمعًا حسب المركز والقرية
- 📊 التقارير والملخصات والتحليلات وروابط التفاصيل
- 🌐 بوابة العملاء: طلبات الصيانة، الشكاوى، الأسئلة، المقالات والشريط الإعلاني
- 🛡️ الضمان وسجل الحالة

## التشغيل

افتح `index.html` في المتصفح، أو ثبّت التطبيق على الهاتف بعد أول تحميل. صفحات الموظفين تتطلب تسجيل الدخول عندما تكون مصادقة Firebase مفعلة. بوابة العملاء لها صفحات وملفات تشغيل مستقلة (`portal.html` و`portal-admin.html`).

## المزامنة والبيانات

- `firebase-sync.js` يربط بيانات التشغيل المحلية بمجموعات Firebase عند توفر SDK والاتصال.
- المزامنة تدعم العمل أوفلاين: التعديل يُحفظ في IndexedDB محليًا ثم يُرفع عند عودة الإنترنت.
- كل جهاز يملك قاعدة محلية خاصة به، لذلك يجب التأكد من اكتمال المزامنة قبل الانتقال بين الأجهزة.
- لا تحذف سجلات كثيرة دفعة واحدة من قاعدة البيانات المحلية دون مراجعة تحذير الحذف؛ النظام يحمي من المسح الجماعي للسحابة.
- `firestore.rules` هي القواعد الحالية، و`firestore.rules.proposed` اقتراح منفصل يحتاج مراجعة ونشرًا مستقلًا.
- مفتاح Firebase الظاهر في الواجهة ليس سرًا؛ الحماية الفعلية تكون عبر قواعد Firestore وتقييد النطاقات في إعدادات Firebase.

## استقبال مكالمة مشتركة من تطبيق تسجيل المكالمات

بعد تثبيت التطبيق كـ PWA، إذا اخترت «الورشة الفنية» من مشاركة تسجيل مكالمة، تفتح صفحة `share-target.html` بفورم أمر شغل سريع مع محاولة تحديد العميل تلقائيًا. إذا كان هناك أمر مفتوح مناسب، يعرض النظام الإلحاق به بدل إنشاء تكرار. المكالمات التي لم تتحول لأوامر تظهر في `pending-calls.html`.

راجع `manifest.json` (`share_target`) و`service-worker.js` للتفاصيل.

## القواعد المالية المهمة

- حركة العربون والتحصيل النهائي المرتبطة بأمر الشغل تستخدم `refKey` ثابتًا، لذلك إعادة حفظ الأمر لا تنشئ حركة جديدة.
- الحركة المحذوفة يدويًا لا تعود تلقائيًا عند حفظ الأمر، بينما الحركة التي أزيلت تلقائيًا بسبب مبلغ/محفظة فارغة يمكن إعادة تفعيلها إذا عادت البيانات.
- تعديل الحركة يدويًا يضع `manualOverride` ويحمي التصحيح اليدوي من الكتابة التلقائية اللاحقة.
- بعد إغلاق الأمر، تُثبت بياناته المالية الأساسية ولا تظهر حقول التعديل العادية.
- مرتجع الأمر المغلق خلال المهلة يعيد فتحه ويحذف التحصيل النهائي التلقائي من حركة المحفظة. أي رد مبلغ فعلي للعميل يجب تسجيله كحركة صرف مستقلة.
- زر `🔎 مطابقة الرصيد` في صفحة الحسابات يعرض الحركات المتكررة، الناقصة أو غير المطابقة. الفحص تشخيصي ولا يعدل البيانات تلقائيًا.
- الخزنة النقدية مستقلة؛ التحصيلات المرتبطة بأوامر الشغل لا تُضاف إليها تلقائيًا إلا إذا سجل المستخدم تحويلًا صريحًا.

## منع التكرار

- طلبات بوابة العملاء الجديدة تستخدم معرفًا ثابتًا مشتقًا من العميل والجهاز وبيانات الطلب.
- الشكوى نفسها لنفس العميل والأمر لا تُنشأ مرة أخرى إذا كانت موجودة.
- مزامنة طلبات البوابة إلى أوامر الشغل تبحث عن `portalRequestId` وتُنظف الطلبات القديمة المتكررة قبل إنشاء أمر جديد.
- أرقام الأوامر وحركات المحافظ تُنشأ بطريقة تمنع تكرار المعرفات.

## البنية الحالية

- `workshop-idb.js` — قاعدة التشغيل ومخزن key-value المحلي وواجهة `WFStorage` وترحيل المفاتيح القديمة.
- `shared-data.js` — طبقة البيانات المشتركة (`K`، `get/put`، الإعدادات، `withRollback`).
- `firebase-sync.js` — مزامنة Firebase والعمل أوفلاين وتحويل طلبات البوابة.
- `image-store.js` — تخزين الصور في IndexedDB.
- `migrations.js` — ترحيل البيانات عند رفع `wf_schema_version`.
- `app-requests.js` — دورة أوامر الشغل، الإغلاق، المرتجع والقواعد المالية.
- `app-parts.js` و`app-restock.js` — قطع الغيار والمخزن وحركاته.
- `wallets.js` و`treasury.js` — المحافظ والتحويلات والخزنة المستقلة.
- `app-dashboard-reports.js` و`reports.js` — لوحة الملخصات والتقارير وروابط التفاصيل.
- `workshop-mini-simple-ui.js` — واجهة القوائم والمرشحات المبسطة.
- `portal.html` و`portal-admin.html` و`portal-ticker.js` — بوابة العملاء وإدارتها وشريط الأخبار.
- `app-settings.js` و`app-settings-lists.js` و`app-data-management.js` — الإعدادات والنسخ والاسترجاع.
- `service-worker.js` و`portal-sw.js` — التخزين المؤقت وتحديث نسخ الواجهة.

## الصور

جميع مفاتيح التطبيق القديمة تُستورد مرة واحدة من `localStorage` إلى IndexedDB، ولا تُمسح النسخة القديمة إلا بعد تأكيد نجاح معاملة الاستيراد. الصور تُخزن في IndexedDB بدل وضع base64 داخل مفاتيح البيانات؛ الصور القديمة تُرحّل تلقائيًا عند فتح التطبيق بعد التحديث. النسخة الاحتياطية من إعدادات النظام تشمل الصور، وتظل ملف JSON واحدًا قائمًا بذاته.

## التحقق قبل الإصدار

```text
npm run check
```

ويتضمن ذلك فحص الصياغة واختبارات التاريخ والنسخ والترحيلات والمعاملات والمخزون والمحافظ والبوابة والجودة الأمنية. إذا توفر Chromium يمكن تشغيل:

```text
npm run browser-test
```

## حدود معروفة

- بعض الصفحات القديمة ما زالت تستخدم `onclick` و`innerHTML`، ويجري تحويلها تدريجيًا.
- المزامنة السحابية تعتمد على إعداد Firebase وقواعد Firestore والاتصال؛ لا تعتبر متاحة إذا لم يتم تحميل SDK أو تسجيل الدخول.
- رفع الصور إلى Cloudinary يستخدم إعداد الرفع الموجود في المشروع؛ يجب تقييد الحجم والصيغ من إعدادات الـ preset.
